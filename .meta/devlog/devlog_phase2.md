## 2026-10-25: Phase 2 実装完了

### 1. 今回実装したスコープ
- **データモデル設計 (`ParsedTransaction.kt`)**
  - 経費（支出）と売上（収入）を単一モデルで統合。
  - 電帳法検索3要件（日付・金額・取引先）に加え、確定申告に必要な勘定科目、プラットフォーム手数料、源泉徴収税額、インボイス番号（T+13桁）を網羅。
  - 電帳法準拠のファイル名自動生成 (`toCompliantFileName()`) および `transaction_log.csv` へのエスケープ出力 (`toCsvRow()`) を実装。
- **AIパース処理 (`GeminiTransactionParser.kt`)**
  - Google AI SDK (`com.google.ai.client.generativeai:0.9.0`) を活用。
  - 暗号化保存されたユーザーのAPIキー（BYOK）から直接 `gemini-1.5-flash` を呼び出し。
  - `responseMimeType = "application/json"` と詳細なシステム指示による構造化JSON抽出。
  - Bitmap解析 (`parseReceiptImage`) だけでなく、PDFや各種画像バイナリを直接送れる `blob` 解析 (`parseDocument`) を実装。
  - `kotlinx.serialization` によるフェイルセーフなデシリアライズ。
- **UI & ViewModel (`ExtractionScreen.kt`, `ExtractionViewModel.kt`)**
  - Material 3 に準拠したダークテーマUI。
  - フォトピッカーによる画像選択および即時AIパース。
  - 実機やエミュレータで即座に動作確認できる「経費デモ」「売上デモ」投入ボタン。
  - 抽出結果の確認・手修正フォーム、電帳法ファイル名のリアルタイムプレビュー。
- **自動テスト (`TransactionDataTest.kt`)**
  - 経費・収入JSONのデシリアライズ検証。
  - 電帳法ファイル名のサニタイズ検証。
  - CSV特殊文字（カンマ、ダブルクォート、改行）のエスケープ検証。
  - すべてのテストがパス（4/4 PASS）。

## 2. 開発・設計のリアルな試行錯誤ログ（noteネタ帳）

### ① なぜ OCR＋正規表現 を捨てて、小型マルチモーダルLLMにしたのか？
* **従来のOCRアプローチの壁:**
  * スマホカメラで撮ったレシートは、影、折り目、斜め撮影、感熱紙の薄れなどノイズだらけ。
  * 「合計」なのか「小計」なのか「お預かり」なのかを正規表現で判別しようとすると、店舗ごとの無数の表記揺れルール（「合 計」「TOTAL」「お買上計」など）をメンテナンスし続ける地獄に陥る。
  * 特に副業特有の「プラットフォーム売上明細（note、ココナラ、AdSense等）」はレイアウトが全く異なり、正規表現での自動化はほぼ不可能。
* **Gemini 1.5 Flash の優位性:**
  * 小型マルチモーダルモデルであるため、推論コストが極めて安い（BYOK無料枠で月数百枚程度なら余裕で無料範囲内）。
  * 単に文字を読むだけでなく、「どれが最終的な支払総額か」「どれがプラットフォーム手数料で、どれが源泉徴収税か」という文脈を理解して適切にフィールド分割してくれる。

### ② 経費と収入の「単一スキーマ統合」という割り切り
* 会計ソフトは経費と売上で入力導線が分かれていることが多いが、個人開発者・副業エンジニアの申告は「1行1仕訳」のCSV台帳で十分。
* スキーマに `fee`（手数料）と `withholding_tax`（源泉徴収税）を含めることで、売上明細書から「売上高」「支払手数料」「源泉所得税」の確定申告3点セットを一撃で分解抽出できる設計にした。

### ③ Android公式SDKでのバイナリ送信 (`blob`) の威力
* カメラで撮った写真だけでなく、ブラウザからダウンロードした領収書PDFやスクショを共有インテント経由でパースしたい。
* SDKの `content { blob(mimeType, bytes) }` を利用することで、端末側でPDFを画像にラスタライズする重たい処理を挟むことなく、PDFバイナリのままGeminiに直接マルチモーダル解析させることができた。

## 4. 本番API実測ベンチマーク検証（BYOK・実領収書PDF投入）

ユーザーから提供された実際の領収書PDF（約169KB、業務スーパー南佐賀店のクレジットカード利用領収証）および実際のBYOKキーを用いて、APIエンドポイントへの実測テストを実施。

### ① 発見された技術的ファクト（モデル世代交代）
* 構想メモで想定していた `gemini-1.5-flash` および `gemini-2.5-flash` は新規ユーザー向け提供が終了しており、HTTP 404（Model Not Found）が返却された。
* Google の API エラーメッセージで明示的に後継モデルへの移行が案内されたため、検証を実施。
* `gemini-3.8-flash` はスパイク需要で一時的な 503（UNAVAILABLE）となったが、軽量モデル **`gemini-3.1-flash-lite`** が極めて安定かつ高速に稼働することを確認。アプリ側のデフォルトモデルもこちらに追従させた。

### ② 定量実測値（ベンチマーク）
* **解析対象:** 実領収書 PDF (169,462 bytes)
* **使用モデル:** `gemini-3.1-flash-lite`
* **API応答時間:** **3.03 秒**
* **消費トークン数:**
  * プロンプト入力: 1,148 tokens
  * 出力トークン: 122 tokens
  * 合計: 1,270 tokens

* 「日付」「金額」「取引先名」の電帳法検索3要件およびインボイス番号（`T2140001041812`）が、一切の文字化けや補正なしで完璧に抽出された。

### ⑤ 有料枠（Pay-as-you-go）移行時のコスト試算（n=1 実測値ベース）
* 前提: 入力 1,148 tokens / 出力 122 tokens、1ドル＝150円換算
* `gemini-3.1-flash-lite`: 約 $0.000470（**約 0.07 円 / 回**）
  * 100枚で約 7.1 円、500枚で約 35.3 円
* `gemini-3.8-flash`: 約 $0.001319（**約 0.20 円 / 回**）
  * 100枚で約 19.8 円、500枚で約 98.9 円
* 留意点: 本数値は現時点で n=1 の単発測定結果であり、今後手書き領収書やWeb売上明細など異なるフォーマットのサンプル数を増やしてばらつきを検証予定。
