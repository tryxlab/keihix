# 【KeihiX開発日記#1】月額課金したくない個人開発者が、サーバー代0円・個人情報保持ゼロの「レシート＆収入管理アプリ」を考え始めた話

確定申告・電帳法対応アプリ「KeihiX」をゼロから自作する開発日記（#1）です。

---

こんにちは。個人開発や副業でコードを書いているエンジニアです。

副業や個人開発で少しずつ売上や経費が発生するようになってくると、避けて通れないのが **「確定申告」** と **「電子帳簿保存法（電帳法）」** の対応です。

freeeやマネーフォワードなどのクラウド会計ソフトは機能が充実していますが、月に5〜10件程度の取引規模の場合、**年間約1.2万〜1.5万円程度のサブスクリプション費用** はランニングコストとしてやや重く感じられます。一方で、手作業のスプレッドシート入力や手動ファイル整理に頼ると、確定申告前の時期に領収書PDFやカード明細の整理にまとまった時間が取られてしまいます。

そこで今回、**「維持費をかけず、日々の保存・入力の手間を最小限に抑える自分用の管理アプリ（KeihiX）」** を作ってみることにしました。

完成したノウハウをまとめるというよりは、**「実際に手を動かして作りながら、考えたことやハマったポイントを書き残していく開発日記」** というスタンスで不定期に書いていこうと思います。

第1回となる今回は、最初の「Vercel ＋ Firebaseでサクッと作ろう」という構想から、なぜ **「サーバーを持たず、個人情報も保持しない設計（ゼロ・インフラ ＋ BYOK）」** に落ち着いたのか、その試行錯誤のメモをまとめます。

## 1. 初期検討：Vercel ＋ FirebaseによるWebアプリ案

最初に検討したのは、個人開発で標準的な構成です。

* **フロントエンド / バックエンド:** Vercel (Next.js / App Router)
* **ストレージ:** Firebase Cloud Storage（領収書PDF・画像）
* **データベース:** Firestore（取引日、金額、取引先、勘定科目）
* **解析:** Gemini Flash API（OCR ＋ メタデータ抽出）

この構成であれば、無料枠の範囲内でWebアプリを構築でき、PCやスマートフォンのブラウザからファイルをアップロードして管理する運用が可能です。

しかし、仕様を詰めていく中で、個人で運用するツールとしての **運用・セキュリティ上の課題** が見えてきました。

### 検討で見えた2つの課題

1. **他者の機密データを保管する責任**
   将来的にオープンなWebサービスとして公開した場合、領収書の画像や取引先、売上金額といったプライベートなデータを開発者側のFirebaseプロジェクトに保管することになります。暗号化や権限分離を行ったとしても、個人情報保護の観点からセキュリティ監視やバックアップの責任が開発者側に発生します。

2. **従量課金インフラの運用リスク**
   無料枠が用意されているとはいえ、ストレージ容量の増加や予期せぬリクエスト増、スパム等によって課金が発生するリスクを完全にゼロにはできません。少額の副業収益を管理するためのツールに対して、インフラの維持管理コストを意識し続けるのは合理的ではないと判断しました。

## 2. 採用した設計：「ゼロ・インフラ ＋ BYOK（Bring Your Own Key）」

そこで、開発者がサーバーやDBを運用する形を避け、**「データとAPI利用権をすべてユーザー環境側で完結させる」** 方向へ方針を切り替えました。

具体的には、**「Android端末ローカル ＋ ユーザー自身のGoogle Drive ＋ ユーザー自身のGemini APIキー（BYOK）」** という構成です。

### 全体構成図

```text
[ユーザー操作: カメラ撮影 / PDF・画像共有インテント]
       │
       ▼
[Android アプリ (端末内完結)]
  ├─ 1. Gemini 1.5 Flash API (BYOK)
  │       └─ 端末から直接通信。画像/PDFからメタデータを構造化抽出
  ├─ 2. ローカル検証・UI修正
  │       └─ 抽出結果の確認と必要に応じた手修正
  └─ 3. Google Drive API (OAuth 2.0: scope 'drive.file')
          └─ バックグラウンドで非同期アップロード
       │
       ▼
[保存先: ユーザー本人の Google Drive]
  └── 確定申告_2026/
        ├── receipts/           (経費の画像・PDF)
        ├── incomes/            (収入の支払明細・請求書控えPDF)
        └── transaction_log.csv (統合トランザクション台帳)
```

この構成には以下の特徴があります。

* **開発者側のインフラ運用費が0円:** サーバーやDBをホスティングしないため、インフラの維持コストが発生しません。
* **機密データを開発者が預からない構造:** 領収書ファイルや取引ログはユーザー自身のGoogle Driveに直接保存されます。
* **Gemini APIの無料枠活用 (BYOK):** Google AI Studioで発行したAPIキーを端末内の安全な領域（ `EncryptedSharedPreferences` ）に保存し、端末から直接Googleのエンドポイントへリクエストを送ります。

## 3. 電子帳簿保存法（電帳法）の要件への対応方針

副業規模であっても、Webやメール経由で受領した電子領収書（PDFやスクリーンショット）は、電帳法上の「電子取引」に該当するため、要件に沿った保存が必要です。

本アプリでは、専用のSaaSを契約せずに、制度上認められている方法を組み合わせて要件を満たす設計にしています。

### ① 改ざん防止措置：国税庁ひな形の事務処理規程を採用
電帳法の電子取引データ保存では、訂正・削除の履歴を残すシステムを利用するか、タイムスタンプを付与するか、もしくは **「訂正削除の防止に関する事務処理規程」** を定めて運用することが認められています。

個人事業主向けには国税庁から規程のひな形が公開されているため、これを準備して備え付けておくことで、有償のタイムスタンプAPI等を使わずに法要件を満たすことが可能です。
アプリ内およびリポジトリにも、この規程のテンプレートを同梱する方針としています。

### ② 検索3要件：「ファイル名 ＋ CSV台帳」での充足
法律上、保存データは「取引年月日」「取引金額」「取引先名」で検索できる状態にしておく必要があります。

本設計では、以下のシンプルな運用で対応します。
1. **Google Drive上のファイル命名規則:**
   `YYYYMMDD_金額_取引先.pdf` （例: `20261022_1980_Amazon.pdf` ）
2. **同一フォルダ内のCSV台帳 (`transaction_log.csv`):**
   アップロード時に日時、金額、取引先、科目、Drive内ファイルパスを行として追記。

Google Driveの標準検索機能や、CSVファイルをスプレッドシート等で開いてフィルタリングすることで、法定の検索要件を満たすことができます。

## 4. クライアントをAndroidアプリにした理由

クライアント環境としてWeb（PWA）ではなくAndroidネイティブを選定した最大の理由は、**OSの「共有メニュー（Share Target）」との親和性** です。

領収書や請求書が発生するタイミングは、以下のように日常の端末操作の中に分散しています。
* ブラウザで領収書PDFをダウンロードしたとき
* メーラーで支払通知を受信したとき
* カフェ等で紙のレシートを受け取ったとき

Webアプリの場合、「ブラウザを開いてログインし、ファイル選択ダイアログから対象ファイルを探す」というステップが必要です。
Androidアプリであれば、**PDFビューアやブラウザの「共有」ボタンから直接アプリを呼び出せる** ため、保存にかかる画面遷移と手数を減らすことができます。

```text
[ブラウザ / PDFビューア] ──(共有メニュー)──> [KeihiX] ──(自動抽出)──> [保存完了]
```

## 5. データ設計：経費と収入を単一スキーマで管理

一般的なレシート読み取りアプリは経費（支出）の管理に特化していることが多いですが、副業の確定申告では **プラットフォーム等からの売上（収入）と、差し引かれた手数料や源泉徴収税の管理** も必要になります。

そこで、データモデルとしては経費・収入を単一のスキーマで定義しています。

* **type (string):** 取引区分（ `expense` または `income` ） / 例: `income`
* **date (string):** 取引日 / 売上計上日（YYYY-MM-DD） / 例: `2026-10-31`
* **amount (integer):** 税込総額（売上額または支払額） / 例: `50000`
* **vendor (string):** 取引先 / 振込元プラットフォーム / 例: `note株式会社`
* **category (string):** 勘定科目（消耗品費、売上など） / 例: `売上`
* **fee (integer / 任意):** プラットフォーム手数料等 / 例: `5000`
* **withholding_tax (integer / 任意):** 源泉徴収税額 / 例: `0`
* **memo (string / 任意):** 摘要メモ / 例: `10月度売上`

Gemini 1.5 Flash の Structured Outputs（JSON Schema）にこの構造を定義し、書類の種類（レシートか支払通知書か）に応じてAIに適切な区分を推定させます。

年末には、出力された `transaction_log.csv` の数値を集計し、**国税庁の「確定申告書等作成コーナー」の収支内訳書へ転記** する運用を想定しています。

本プロジェクトでは以下の通り設計しています。

1. **初回起動時の免責同意ダイアログ:**
   * 本アプリは税理士法に定める助言や税務書類の作成を行うものではない旨。
   * AIによる抽出精度や法的適合性について開発者は保証せず、最終的な申告内容の確認はユーザー自身の責任で行う旨。
   * 上記に同意したユーザーのみ利用可能とする。
2. **規程および免責事項のアプリ内常設:**
   * 設定画面からいつでも免責文面と事務処理規程を確認できるようにする。
