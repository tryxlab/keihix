## 1. 電帳法の合法ハック：高価なタイムスタンプは本当に必要なのか？

個人開発者や副業エンジニアが電帳法（電子取引データの保存義務化）に対応しようと調べると、多くの解説記事で **「タイムスタンプ付与機能」** や **「改ざん防止機能付きの有料クラウドサービス」** が推奨されています。

しかし、個人事業主が月に数件〜数十件程度のAmazonの領収書PDFやSaaSの請求書を保存するためだけに、月額千円単位のサービスを契約するのはコストパフォーマンスが見合いません。

そこで国税庁の法令・通達を改めて調べ直したところ、非常にシンプルで合法的な解決策がありました。

### タイムスタンプに代わる「事務処理規程」の備え付け

国税庁の「電子帳簿保存法一問一答（電子取引関係）」によると、改ざん防止措置として以下の4つのうちいずれかを満たせばよいと定められています。

1. タイムスタンプが付与されたデータを受け取る
2. 授受後、速やかにタイムスタンプを付与する
3. 訂正・削除の防止に関するクラウド等（改ざん防止システム）を利用する
4. **「正当な理由がない訂正・削除の防止に関する事務処理規程」を定め、それに沿って運用・保存する**

この **4番目の「事務処理規程の備え付け」** こそが、ゼロ・インフラで運用するための最大の鍵でした。

国税庁が公式に配布している「個人事業主用の事務処理規程（ひな形）」をダウンロードし、事業主名と日付を記入して手元（ローカルまたはGoogle Drive）に備え付けておくだけで、 **有償のタイムスタンプAPIや認証クラウドを使わなくても適法に電子データを保存できる** のです。

### 検索3要件はどう満たすか？

もうひとつのハードルである「検索要件（取引年月日・取引金額・取引先での検索）」についても、電帳法では **「ファイル名に『日付_金額_取引先』を付与してフォルダ管理する」** または **「ファイル名と連動した索引簿（CSVやスプレッドシート）を作成する」** 方法が明記されています。

KeihiXでは、両方を同時に満たす設計にしました。

* **ファイル自体の命名:** `20260115_1980_Amazon.pdf` のようにリネームしてGoogle Driveの年別フォルダ（`確定申告_2026/receipts/`）へ保存
* **台帳CSVの追記:** 同フォルダ内の `transaction_log.csv` に1行追記（日付、金額、取引先、勘定科目、Driveリンク）

これだけで、Google Drive標準の検索機能とスプレッドシートのフィルタ機能によって、税務調査時の提示要件を満たすことができます。

## 2. 税理士法リスクを避けるための「初回免責ゲート」

電帳法の要件と並んで個人開発アプリが直面するのが **「税理士法」の境界問題** です。

税理士法第52条では、資格を持たない者が「税務相談」や「税務書類の作成」を有償・無償を問わず行うことを禁じています。アプリが「この経費は消耗品費です」と断定したり、自動で申告書を確定させてしまうようなUXにすると、意図せずこの境界に踏み込んでしまう恐れがあります。

そのため、KeihiXでは以下の割り切りをUI設計に組み込みました。

* **AI（Gemini）の抽出結果はあくまで「推測値・下書き」として提示する**
* **ユーザー自身が確認し、納得した上で保存ボタンを押すフローを必須にする**
* **初回起動時に「税務助言を行わないツールであり、申告は自己責任であること」への明確な同意を求める**

単なる利用規約の読み飛ばしを防ぐため、初回起動時は3つの確認項目（税務助言非該当、事務処理規程運用、BYOKとゼロインフラ）すべてにチェックを入れないとメイン機能に進めない **「ブロック型免責画面」** を作りました。

また、ユーザーが国税庁のウェブサイトを探し回らなくて済むよう、国税庁ひな形ベースの事務処理規程テキストをアプリ内にあらかじめアセットとして同梱し、画面上のボタンから1タップで全文確認・共有できるようにしています。

## 3. 【開発の脱線】Android Studioすら不要だった？ CLIだけで実機を動かした話

さて、ここからが今回一番エンジニアとして面白かった試行錯誤の話です。

画面のKotlinコード（Jetpack Compose）を書き終え、「さあ画面を動かして動作確認しよう」となったとき、ふと立ち止まりました。

> **「そもそも、アプリを実機で動かすためだけに、数GBもある重たい Android Studio をインストールする必要はあるのだろうか？」**

通常のAndroidアプリ開発入門では、「まず Android Studio をダウンロードし、長いインストール待ちを経てIDEを起動する」のが定番です。しかし、Android Studio の実態は IntelliJ IDEA をベースにした統合開発環境であり、 **ビルドそのものは Gradle というコマンドラインツールが裏で動いているだけ** です。

「もしかして、最小限のツールだけでターミナルから実機へ直接ビルド＆転送できるのでは？」と思い立ち、試してみることにしました。

### 揃えたのは最小限の3つだけ

Windowsのパッケージマネージャー（winget）と公式アーカイブを使い、以下の3点だけを手元に用意しました。

* **JDK 17:** `Microsoft.OpenJDK.17`（Gradleを動かすJava環境）
* **Android SDK 35 ＋ build-tools:** Google公式の `commandlinetools` をダウンロードし、`sdkmanager` でSDK 35のみをピンポイントで取得
* **Platform-Tools (`adb`):** `Google.PlatformTools`（実機スマホとUSB通信するコマンド）

Android Studio本体は一切インストールしていません。もちろん、IDEがあればグラフィカルなレイアウトプレビューやデバッグGUIが使えるメリットはありますが、今回は「とにかくPCを軽く保ち、CLIで素早くイテレーションを回す」という割り切りを選びました。

### わずか 15秒 の爆速ビルド

プロジェクト直下で Gradle Wrapper を動かし、デバッグ用APKをビルドしてみます。

```powershell
.\gradlew.bat assembleDebug
```

初回こそ必要なライブラリのダウンロードが入るものの、2回目以降のビルド時間は **わずか 15秒〜17秒**。

生成された `app-debug.apk` のサイズは約 **23.5MB**。重たいGUI IDEを一切立ち上げていないため、PCのメモリもCPUファンも極めて静かなままです。

### USBで繋いだ実機（Pixel 9a）へ即座に流し込む

ビルドが通ったら、手元の実機スマートフォン（Google Pixel 9a）をUSBケーブルでPCに繋ぎ、開発者向けオプションの「USBデバッグ」をONにします。

ターミナルから以下のコマンドを順番に叩くだけで、実機へのインストールから起動、画面キャプチャまでが一気に完了しました。

```powershell
# 1. 実機へAPKを転送・インストール
adb install -r app/build/outputs/apk/debug/app-debug.apk

# 2. アプリのメイン画面を自動起動
adb shell am start -n com.keihix.app.debug/com.keihix.app.MainActivity

# 3. 実機画面の生スクリーンショットをPCに保存
adb exec-out screencap -p > Docs/images/real_pixel9a_disclaimer.png
```

## 4. 実機で動いて初めて気づいた「画面の被り」

こうして実機 Pixel 9a にアプリが立ち上がった瞬間、 **「実機で動かして本当によかった」** と痛感する出来事がありました。

最初の画面キャプチャを撮ってみたところ、画面上部のステータスバー（時計やWi-Fiアイコン、そしてPixelの中央カメラホール）と、アプリの「KeihiX 免責事項の確認」というタイトル文字が **見事に重なってしまっていた** のです。

最新の Android では画面の隅々まで描画する「Edge-to-Edge」が標準になっているため、ステータスバーやナビゲーションバーの領域を考慮したインセット（余白）をコード側で明示的に指定しないと、文字が食い込んでしまいます。

モックアップ画像やエディタ上だけでは見落としがちな、実機ならではのリアルな罠でした。

### インセット修正で一気に洗練されたUIへ

Compose の `Modifier.statusBarsPadding()` と `navigationBarsPadding()` をルートの Column に追加し、再度ビルドして実機へ転送しました。

```kotlin
Column(
    modifier = Modifier
        .fillMaxSize()
        .statusBarsPadding()     // カメラホール・ステータスバーの余白を自動確保
        .navigationBarsPadding() // 画面下のジェスチャーバーの余白を自動確保
        .padding(horizontal = 20.dp, vertical = 16.dp)
) {
    // ヘッダーやカードUI
}
```

修正後の実機スクリーンショットがこちらです。

### 実機（Pixel 9a）で動いた実際の画面

* **画面1: 初回免責事項・電帳法同意画面**
  カメラホールを綺麗に避けてタイトルが配置され、3つの注意点カード、事務処理規程の確認リンク、そしてチェックボックスが並びます。3つすべてにチェックを入れるまで、一番下の「同意してはじめる」ボタンは押せない設計です。
  *(画像ファイル: `Docs/images/real_pixel9a_disclaimer.png`)*

* **画面2: 設定・BYOK（Gemini APIキー設定）画面**
  チェックを入れて同意ボタンを押すと、画面が遷移して設定画面が現れます。Gemini APIキーのマスク入力欄、接続テストボタン、そして Google Drive の最小権限スコープ（`drive.file`）のステータスが表示されます。
  *(画像ファイル: `Docs/images/real_pixel9a_settings.png`)*

手元のスマホでボタンをタップした瞬間に小気味よく画面が切り替わり、自分の書いたコードが端末上で生き生きと動く感覚は、個人開発ならではの格別な楽しさがあります。

## 5. まとめと次回

今回は、実装の土台となる以下のステップを記録しました。

* **高価なシステムに頼らない電帳法ハック:** 国税庁ひな形の「事務処理規程」備え付けと、ファイル名＋CSV台帳による検索要件のクリア
* **税理士法リスクをクリアするUI設計:** 初回起動時のブロック型免責画面と、暗号化領域（`EncryptedSharedPreferences`）によるAPIキーのローカル保持
* **超軽量なCLI実機開発:** Android Studioを使わず、JDKとadbだけで15秒ビルド＆実機Pixel 9aへの直接転送

巨大なIDEのセットアップに時間を取られず、最小限のコマンドライン環境でサクサク実機ビルドを回せる開発フローが整ったのは、今後の開発スピードにとっても大きな収穫でした。

次回（#3）は、いよいよコア機能である **「Gemini 1.5 Flashによる領収書・明細の構造化抽出（Structured Outputs）と、BYOKの安全な接続テスト」** の実装に入っていく予定です。

開発中のコードや事務処理規程のテキストは、GitHubリポジトリで順次公開しています。
