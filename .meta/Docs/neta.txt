 個人事業主としての経費と収入を管理するのにfreeeなどは便利と思いますが、ほかにはどういう方法がよさそうですか

飲食業とかではないので副業だしそんなに頻繁ではないですが、確定申告のためにまとめておきたい

副業かつ取引件数がそこまで多くない場合、月額・年額のサブスクリプション費用がかかるクラウド会計ソフト（freeeやマネーフォワードなど）を使わずに管理する方法は十分に現実的です。

確定申告（青色申告10万円控除、または白色申告、雑所得申告）を見据えた場合、主な選択肢は以下の4つに整理できます。

おすすめの具体的アプローチ
1. スプレッドシート（またはExcel）による「1行1仕訳」管理

取引頻度が低ければ、最も身軽でメンテナンス性が高い方法です。

    運用の基本構成

        日付 / 区分（収入 or 経費） / 勘定科目（消耗品費、通信費、旅費交通費、支払手数料など） / 金額 / 取引先・内容 / 支払方法（専用カード、現金など）

    確定申告との接続

        ピボットテーブル等で「勘定科目ごとの年間合計金額」を出すだけで、国税庁の「確定申告書等作成コーナー」の収支内訳書や決算書にそのまま数字を転記できます。

2. 専用のクレジットカード・銀行口座による「導線の分離」

管理手法そのものと同じくらい効果的なのが、副業用の決済手段をプライベートから分けることです。

    副業用の支出・受取口座を1つに集約しておけば、毎月帳簿をつけなくても「年末にその口座の通帳やWeb明細（CSV）をダウンロードして仕訳をつける」だけで申告準備の8割が完了します。

3. クラウドサービスの無料枠活用

    やよいの白色申告 オンライン: ずっと無料で収支内訳書の作成まで利用可能です（白色申告の場合）。

    マネーフォワード クラウド確定申告: 無料プランでも「年間仕訳件数50件まで」であれば継続利用できるため、年間の取引が少なければ無料枠内に収まることがあります。

現在の副業の申告形態（青色申告で55万・65万円控除を狙うか、白色申告・10万円控除・雑所得か）や、年間の仕訳件数（月数件程度か、数十件規模か）に合わせて、どの管理フローが一番ストレスなく運用できそうか検討してみてください。

領収書は電子であればいいんだっけ？ならば簡単なものをvercel+firebaseで作るのはどう？

領収書（レシート）の電子保存は、ルールさえ押さえれば完全に電子のままで問題ありません。Vercel ＋ Firebase（Next.js ＋ Cloud Storage / Firestore） での自作は、技術的にも運用の自由度としても非常に相性が良い構成です。

自作にあたって押さえておくべき「電子帳簿保存法（電帳法）の要件」と「システム設計の勘所」を整理しました。
1. 領収書の電子保存ルール（電帳法・スキャナ保存 & 電子取引）

領収書には「紙でもらったもの」と「Webやメールで届いた電子データ」の2種類があり、要件が少し異なります。

    Web・メール等で受領した電子領収書（PDFやスクショ）

        電子保存が義務です（紙に印刷して原本代わりにするのは原則不可）。

        満たすべき要件は主に次の2点です：

            改ざん防止の措置: タイムスタンプ付与、または「訂正削除の防止に関する事務処理規程」を定めて運用する（個人事業主は国税庁のひな形规程を1枚作って保管しておくだけでOK）。

            検索機能の確保: 「取引年月日」「取引金額」「取引先名」で検索・抽出できること。

    紙でもらったレシート

        スマホで撮影してアップロードし、要件を満たせば紙原本は破棄可能です（ただし件数が少ないなら、紙のまま月別クリアファイル等に突っ込んで保管するほうがシステム要件の厳格化を避けられて手軽な場合もあります）。

2. Vercel ＋ Firebase で自作するメリットと構成案

副業レベルの規模であれば、月額コスト完全ゼロ（無料枠内）で自分の使い勝手に特化したUIを作れます。

[スマホ / PC] 
  └─ 写真・PDFアップロード（ドラッグ＆ドロップ or スマホカメラ直）
      ↓
[Vercel (Next.js / App Router)]
  ├─ プレビュー表示
  ├─ OCR連携（Google Cloud Vision API または無料枠の小型LLM/Gemini Flash等）
  │   → 日付・金額・取引先名を自動抽出
  └─ 保存処理
      ↓
[Firebase]
  ├─ Cloud Storage: 領収書ファイル（画像 / PDF）
  └─ Firestore: メタデータ（日付、金額、取引先、勘定科目、ステータス、Storageパス）

自作する際の設計ポイント

    検索要件への対応（電帳法対策）

        Firestoreに date（Timestamp or YYYY-MM-DD）、amount（number）、vendor（string） を持たせ、複合インデックスまたは管理画面上のフィルタで「日付範囲・金額範囲・取引先名」で絞り込めるようにしておけば法要件をクリアできます。

    タイムスタンプ代わりの規程運用

        高価な認定タイムスタンプをAPI経由で打つ必要はありません。国税庁のウェブサイトにある「電子取引データの訂正及び削除の防止に関する事務処理規程（個人事業主用）」をダウンロードして名前を入れ、保管しておくだけで法律上クリアされます。

    OCRによるメタデータ自動入力（おすすめ）

        レシートをアップロードした際、Firebase FunctionsやNext.jsのRoute HandlerからOCR（またはGemini API等）に投げて「日付・金額・店名」を自動抽出してフォーム初期値に入れると、手入力の手間が激減します。

    CSVエクスポート機能

        年末に「日付 / 勘定科目 / 取引先 / 金額 / メモ」の形式でCSV出力できるようにしておけば、国税庁の確定申告書等作成コーナーへの転記やスプレッドシートへの貼り付けが瞬時に終わります。

3. 注意点（自作 vs 既存ツールの手軽さ）

    開発コストとの見合い

        画面構築やStorageのセキュアルール設定など、初期構築に数時間〜1日程度の手間はかかります。

        「自分好みのUIでさくさく溜めたい」「将来的に他の副業ツールと統合したい」という意図があれば、非常に満足度の高いツールになります。

    超シンプルに済ませる代替案

        もし「開発に時間を割くほどではない」と感じる場合は、Googleドライブに「20261022_1500_アマゾン.pdf」といった命名規則で放り込み、スプレッドシートに記録するだけでも電帳法の要件（ファイル名による検索要件充足）を満たせます。

技術的・法的な懸念点はほとんどなく、年間利用料ゼロで完全カスタマイズできるため、Web技術に慣れている方には非常に理にかなったアプローチです。

noteでウケる技術的な見どころ・設計ポイント
1. OCRではなく「小型マルチモーダルLLM」で一発構造化

従来のOCRエンジン（Vision API等）だと「文字列のバウンディングボックス抽出 → 正規表現で日付や金額をパース」という泥臭い正規化処理が必要でした。
ここを Gemini 1.5 Flash の Structured Outputs（JSON Schema指定） に任せることで、コード数十行で高精度な抽出が完結します。

    プロンプトとスキーマのイメージ
    TypeScript

    // app/api/extract/route.ts
    import { GoogleGenerativeAI, SchemaType } from "@google/generative-ai";

    const schema = {
      type: SchemaType.OBJECT,
      properties: {
        date: { type: SchemaType.STRING, description: "YYYY-MM-DD形式の取引日" },
        amount: { type: SchemaType.INTEGER, description: "支払総額（税込）" },
        vendor: { type: SchemaType.STRING, description: "発行元・店舗名・会社名" },
        category: { 
          type: SchemaType.STRING, 
          description: "勘定科目の推定（消耗品費、通信費、旅費交通費、会議費、新聞図書費、雑費）" 
        },
      },
      required: ["date", "amount", "vendor", "category"],
    };

    手書き領収書やレイアウトが崩れたレシートでも柔軟に認識できるため、開発記録としてのインパクトも大きいです。

2. 電帳法（電子取引・スキャナ保存）の要件をコードに落とし込む

「電帳法対応」と聞くと仰々しいシステムが必要に見えますが、個人開発レベルで満たすべきポイントは実はシンプルです。

    検索の3要件（Firestoreの設計）

        date (string / timestamp)

        amount (number)

        vendor (string)

        この3項目で範囲検索・複合検索ができるUIと、Firestore複合インデックスを用意する。

    改ざん防止（規程方式）

        高価なタイムスタンプAPIを使わず、国税庁ひな形の「電子取引データの訂正及び削除の防止に関する事務処理規程」を自身で定めてリポジトリやローカルに保管しておく方針を記事で紹介すると、実用的な知恵として読者に喜ばれます。

interface ReceiptDocument {

}

一方で収入の記録はどうでしょうか

副業や個人開発の「収入」は、経費（レシートが日常的に発生する）と比べて「発生頻度が月1〜数件と少ないが、証憑の形式がバラバラ」という特徴があります。

アプリやDriveの設計を破綻させず、同じ思想（ゼロ・インフラ ＋ Google Drive ＋ 電帳法対応）で収入をどう扱うべきか、具体的な設計と運用方法を整理しました。
1. 収入における証憑（エビデンス）のパターン

副業の収入は、相手やプラットフォームによって手元に残るデータが異なります。

    プラットフォーム売上（note、Google Play、Stripe、App Storeなど）

        請求書ではなく、月次の「支払明細書（Payout Report / Remittance Advice）」のPDFやWeb画面のスクショ。

    クライアントワーク（業務委託・開発受託など）

        自身が発行した「請求書の控え（PDF）」、または先方から送られてくる「支払調書」。

    銀行振込の入金データ

        通帳の該当行やオンラインバンキングの入金明細スクショ・CSV。

電帳法上、「Webからダウンロードした月次レポートPDF」や「自分で送った請求書PDFの控え」も立派な電子取引データなので、経費のレシートと全く同じルール（日付・金額・取引先の検索要件）で保管する必要があります。
2. アプリ・Google Driveでの統合設計案

経費アプリの枠組みをそのまま拡張して、「タイプ（経費 / 収入）」を切り替えられる設計にするのが最も綺麗です。
(1) UI側の設計（経費/収入のトグル切り替え）

共有インテントやアップロード画面で、ワンタップで区分を選べるようにします。

    種別: 経費 (Expense) / 収入 (Income)

    収入に切り替えた場合、Geminiへのプロンプトで推定する「勘定科目」を収入用の科目にスイッチします。

        収入の勘定科目候補：売上（売掛金）、雑収入 など。

(2) Geminiによる抽出（Structured Outputs の微修正）

支払明細書や請求書控えのPDF/スクショを投げた際も、基本の抽出項目は経費と同一で機能します。
TypeScript

interface IncomeExtraction {
  type: "income";
  date: string;          // 発生日 / 入金日 (YYYY-MM-DD)
  amount: number;        // 入金額（または売上総額）
  vendor: string;        // 取引先名 / プラットフォーム名（例: "note株式会社", "Google LLC"）
  fee?: number;          // 手数料（プラットフォーム手数料が引かれている場合）
  category: "売上" | "雑収入";
}

※ プラットフォーム売上の場合、「売上総額」から「プラットフォーム手数料」が引かれて振り込まれるケースが多いため、可能なら fee（支払手数料） も一緒に拾えると確定申告が劇的に楽になります（総額で売上を立て、手数料を経費にするのが税務上の原則のため）。
(3) Google Drive のフォルダ構成

同じルートフォルダ配下に incomes と expenses を並べるか、単一のファイル名プレフィックスで区別します。
Plaintext

My Drive/
  └── 確定申告_2026/

        │     └── 20261022_1980_Amazon.pdf

        │     └── 20261031_50000_note株式会社.pdf

3. 個人開発・副業ならではの「収入記録」のリアルな落とし穴

note記事の「開発ノウハウ」や「免責・ガイド」に盛り込むと価値が高くなる税務上のポイントです。

    「入金日」と「売上計上日（発生主義）」のズレ

        例：10月末締めの売上が、実際に口座に振り込まれるのは11月末や12月。

        税務上は「権利が確定した日（10月末）」の日付で売上を立てるのが原則（発生主義）です。アプリで読み取る際は「支払明細の発行日・確定日」を日付として取得するのが安全です。

    源泉徴収税額の扱い

        原稿料や業務委託の場合、先方が源泉徴収（約10.21%）を引いて振り込んでくることがあります。

        「手取り入金額」ではなく「源泉徴収前の総額」を売上として記録する必要があるため、Geminiのプロンプトで「総額・源泉徴収税・差引支払額」が明細にあれば抜き出すようにしておくと親切です。

結論としての落としどころ

収入の記録も「明細PDFやスクショを共有メニューからアプリに投げて、Driveに放り込む」という同じパイプラインに一本化するのが最も自然です。

件数が月1〜数件程度であれば、UIに「収入」のトグルを1つ足すだけで、経費と収入が完全に同一の思想・同じCSVで完結するため、ユーザーの手間もアプリの実装負荷も最小限で済みます。

        最終的な税務判断・申告内容の確認はユーザーの自己責任とする。

そのうえでkeihixで違和感ないかな

keihix（ケイヒックス）で全く違和感はありません。むしろこのプロジェクトの狙いに対して非常に優れたネーミングです。

違和感がない理由と、リポジトリ・ストア・note展開における強みを整理しました。
1. ネーミングとしての強み

    発音しやすく、記憶に残りやすい

        「経費（Keihi）」＋「X（DX / eXpress / 未知・拡張）」の組み合わせは、音読したときの語感が軽快（「ケイヒックス」）で、口頭でもテキストでも通りが良いです。

    リポジトリ名・パッケージ名としての収まりが良い

        全部小文字の keihix は、GitHubのURL（[github.com/.../keihix](https://github.com/.../keihix)）、npm/gradleパッケージ名（jp.xxx.keihix）、CLIコマンドやブランチ名として打つ際にも短く、ハイフンなしで美しく収まります。

    Google Playストアでの見栄え

        アプリ名として「KeihiX - 確定申告・電帳法レシート管理」のように冠すると、単なるツールアプリではなく「洗練されたユーティリティブランド」のような印象を与えられます。アイコンのデザイン（KとXをモチーフにした幾何学デザインなど）も作りやすいです。

2. note記事・発信面でのフック

「freeeの代替を自作した」という説明よりも、「KeihiX というゼロ・インフラの確定申告ハックアプリを作った」と固有名詞化されているほうが、読者の印象に強く残ります。

    記事タイトル例:

        「確定申告の月額課金から解放されたくて『KeihiX』というAndroidアプリを作った話」

        「サーバー代0円・BYOKで動く電帳法対応スタック『KeihiX』の設計思想」

表記と使い分けの推奨

    GitHubリポジトリ / パッケージ名: keihix（小文字統一）

    アプリ表示名 / ドキュメント・note表記: KeihiX（キャメルケースで視認性を上げる）

「経費ツールであること」が直感的に伝わりつつ、野暮ったくないテック感がしっかり出ているため、この名前で進めるのがベストです。

noteや開発過程の記録についても、aiと会話しながらgitにissueを起こして、aiにnote記事を書いてもらおうと思っています

それに対するメタのspecをフォルダに格納しておこうと思うので、その計画も書いて

「AIと壁打ちしながらGitHub Issueを立て、実装と並行してAIにnote記事の下書きを生成させる」というワークフローは、開発ログの鮮度を落とさず発信コストを最小化する極めて合理的な仕組みです。

リポジトリ直下に配置するメタ設計用フォルダ（例: .meta/ または docs/meta/）に格納すべきドキュメント群と、その運用計画をまとめました。
メタ開発・note自動生成パイプライン計画
1. フォルダ構成案 (.meta/)

2. 格納するメタSpecドキュメント定義
(1) 開発＆ログ兼用 Issue テンプレート (.meta/templates/ISSUE_DEV_LOG.md)

noteの素材をIssueの段階で構造化して溜めるためのフォーマットです。
Markdown

---
name: Dev Task & Note Log
about: 開発タスクの管理とnote記事の素材蓄積
---

## 1. 課題と背景 (Why)
- 何に困っていたか / なぜこの実装・検証が必要か

## 2. 検討したアプローチと決定事項 (How & Decision)
- 没案とその理由
- 採用した設計（技術選定の理由）

## 3. 実装の要点 (Code & Architecture)
- ハマったポイントとその解決策
- 実際のコードスニペット / 設定

## 4. note用クリップ (Note Clips)
- [ ] 読者に伝えたい知見・学び（1〜2行）
- [ ] 添付予定のスクショ / ログ

(2) Issue起票用プロンプト (.meta/prompts/issue-creator.md)

AIとの壁打ち終了時に投げて、Issue本文を一発出力させるプロンプトです。
Markdown

以下の会話内容を要約し、プロジェクトの「Dev Task & Note Log」フォーマットに従って
GitHub IssueのタイトルおよびMarkdown本文を作成してください。

特に「なぜその設計にしたのか」「試行錯誤の過程」「noteで読者に刺さるポイント」を
抜け漏れなく含めてください。

(3) note記事生成プロンプト (.meta/prompts/note-generator.md)

クローズしたIssueやコミットログを入力として、noteの初稿を書き起こさせるプロンプトです。
Markdown

あなたは「KeihiX」の開発者です。
添付のクローズ済みIssue内容およびコミット差分をもとに、個人開発者・副業エンジニア向けのnote技術記事（2,000〜3,500文字程度）を執筆してください。

【制約・執筆ルール】
1. トーン＆マナー：`.meta/guidelines/tone-and-manner.md` を遵守すること。
   - 飾り立てた宣伝調ではなく、エンジニアの実践ログとしての率直な語り口。
2. 構成：
   - はじめに（課題意識と結論）
   - なぜこの構成なのか（比較と設計思想）
   - 実装の肝（コード・設定・電帳法ハック）
   - ハマりどころと学び
   - まとめと免責事項
3. 免責条項を末尾に必ず付与すること。

(4) トーン＆マナー・執筆規約 (.meta/guidelines/tone-and-manner.md)

AIが記事を書く際にトーンがぶれないようにするための指針です。

    スタンス:

        「税金や法律の専門家」としてではなく、「自分の手を動かして課題を解決したエンジニア」の目線で書く。

        「こうすべき」と断定せず、「今回のアーキテクチャではこう割り切った」というトレードオフを率直に開示する。

    読者ターゲット:

        副業や個人開発で少額の売上・経費が発生しているが、既存ツールの月額課金に躊躇しているエンジニア。

    必須ルール:

        各記事の末尾に、リポジトリ同梱の「免責条項（税務アドバイスではない旨）」を必ず挿入する。

        リポジトリへのリンク（GitHub URL）を配置し、再現可能なオープンソースであることを示す。

3. 運用サイクル計画（ワークフロー）
Plaintext

[日常のアイデア・課題]
       │
       ▼
1. AIと壁打ちチャット（設計・方針の整理）
       │
       ▼
2. `issue-creator.md` でIssue本文を生成 → GitHubにIssue起票
       │
       ▼
3. 実装作業 & コミット（Issue番号をコミットメッセージに紐付け）
       │
       ▼
4. Issueクローズ時：`note-generator.md` にIssue本文と差分を渡し、note初稿を生成
       │
       ▼
5. 人間が手直し（自分自身の生々しい感想やスクショを補完）してnote公開

このメタSpecをリポジトリ内にコミットしておくことで、開発環境（ClaudeやGemini等）を跨いでも同じ品質とフォーマットでIssue起票とnote執筆が自走できるようになります。
